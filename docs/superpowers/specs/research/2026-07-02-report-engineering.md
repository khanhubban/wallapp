## 1. How industry plans before building

**Production readiness reviews (PRR).** Google formalizes pre-launch quality gates as a PRR whose explicit objectives are verifying a service meets production standards and minimizing incident count/severity [CONFIRMED — 3 votes, verbatim]. (https://sre.google/sre-book/evolving-sre-engagement-model/) The PRR evaluates six production aspects — system architecture & interservice dependencies; instrumentation/metrics/monitoring; emergency response; capacity planning; change management; performance (availability, latency, efficiency) [CONFIRMED — 2 votes, 1 dissent on attribution: the six items are the SRE book's general definition of "production" concerns under "The SRE Engagement Model," not verbatim a PRR checklist — substance stands, framing softened]. (same URL) PRR is a staged process — analysis against checklist, prioritized remediation, training, progressive onboarding — not a one-time sign-off [UNVERIFIED]. Google's Early Engagement model puts reliability review at design time rather than post-launch [UNVERIFIED], and Google reduced per-service readiness cost by codifying production concerns (monitoring, release, capacity) into reusable frameworks [UNVERIFIED]. (all same URL, *inferred*)

**Launch checklists.** Google has run a written Launch Coordination Checklist since ~2005, published as SRE book Appendix E [CONFIRMED — 3 votes, verbatim]. (https://sre.google/sre-book/launch-checklist/) A dedicated Launch Coordination Engineering team (staffed 2004) curates it, credited with "reproducibly reliable launches" [CONFIRMED — 3 votes]. (https://sre.google/sre-book/reliable-product-launches/) Checklist curation is deliberately anti-bloat: adding a question once required VP approval; every item must be substantiated, ideally by a previous launch disaster [UNVERIFIED]. The checklist requires: repeatable builds, canaries under live traffic, staged rollouts [CONFIRMED — 3 votes, verbatim]; per-backend definition of load balancing, rate-limiting, timeout, retry, and error-handling behavior *before* launch [CONFIRMED — 3 votes, verbatim]; graceful degradation planning when third-party dependencies fail, plus mechanisms preventing your own retries from overrunning them [UNVERIFIED]; and launch-timing risk review (hard deadlines, Monday/Friday launches) [UNVERIFIED]. (both checklist URLs)

**Design docs / RFCs.** Google, Facebook, Microsoft, Amazon all use RFC/design-doc processes; Google's variant is "design docs" with a well-known structure (context/scope, goals/non-goals, design, system diagram, APIs, data storage, alternatives, cross-cutting concerns) [UNVERIFIED]. Amazon runs design reviews on technical documents alongside PR/FAQs; Spotify embeds RFCs/ADRs deeply (even for reorgs); LinkedIn has a strong RFC culture [all UNVERIFIED]. Uber adopted formal written planning (DUCK docs) around 2012–13 with <50 engineers — design-doc culture predates scale [UNVERIFIED] — with the stated purpose of org-wide transparency, not just spec [UNVERIFIED]. Recommended workflow: plan before building, capture in a short doc writable in a few hours, distribute broadly, get sign-off from a few senior engineers + future users before coding [UNVERIFIED]. Overhead proportional to risk: skip RFCs for small changes, write one for non-trivial changes with dependencies [UNVERIFIED]. Broadcast RFC review breaks down past ~2,000 engineers (noise, ambiguity, poor discoverability) [UNVERIFIED]. Written plans create accountability and more thorough decisions [UNVERIFIED]. Engineers who write design docs and request reviews ship more maintainable architecture [UNVERIFIED]. (*inferred source: The Pragmatic Engineer, "Scaling Engineering Teams via RFCs"; digest URLs missing*)

**Apply to our design:**
- Write one lightweight design doc (Google structure: goals/non-goals, catalog schema, pointer-flip mechanism, alternatives considered) and have it reviewed before building — Uber adopted this at <50 engineers.
- Build an incident-derived launch checklist seeded with the two verbatim-confirmed SRE items: (a) repeatable publish builds + canary + staged rollout of catalog versions, (b) written timeout/retry/error-handling policy for every client→Firebase Storage call path, defined pre-launch.
- Add a "graceful degradation" checklist item: app fully functions on cached catalog when Firebase Storage/CDN is unreachable, and client retry policy provably cannot storm the bucket.
- Codify publish/validation as reusable pipeline code: one script that validates, uploads, and flips — never manual console operations.

## 2. Data contracts & versioning for static JSON over CDN

**Compatibility semantics (Confluent Schema Registry model).** BACKWARD compatibility = new-schema consumers can read data produced with the previous schema; implies consumers upgrade before producers [CONFIRMED — 3 votes, verbatim]. FORWARD compatibility = data produced with a new schema remains readable by previous-schema consumers — the property a publisher must maintain when consumers (installed app versions) cannot be upgraded first [CONFIRMED — 3 votes, verbatim]. TRANSITIVE variants check against *all* previous versions, not just the latest (BACKWARD_TRANSITIVE: consumer on X reads X, X-1, X-2) — the stronger guarantee needed when many old versions coexist in the field [CONFIRMED — 3 votes, verbatim]. Default mode is BACKWARD non-transitive [UNVERIFIED]. Adding a field with a default value is the canonical safe evolution move [UNVERIFIED]. (https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html)

**Kotlin client mechanics (kotlinx.serialization).** By default the Json decoder *throws* on unknown keys; `ignoreUnknownKeys = true` is the documented forward-compat mechanism for when the catalog adds fields older clients don't know [CONFIRMED — 3 votes, verbatim]. Properties with default values are optional during decoding — missing JSON fields get the default — enabling backward-compatible field addition [CONFIRMED — 3 votes, verbatim]. `coerceInputValues` treats null-for-non-nullable and unknown enum values as missing, applying defaults instead of throwing [UNVERIFIED]. Docs explicitly frame these as schema-evolution tools [UNVERIFIED]. `@JsonNames` / `@JsonIgnoreUnknownKeys` are `@ExperimentalSerializationApi` and may change between releases [UNVERIFIED]. (https://github.com/Kotlin/kotlinx.serialization/blob/master/docs/json.md)

**API-evolution practice.** Only additive changes (new optional fields) are backward compatible; removing/renaming/retyping fields or making optional fields required are breaking within a schema version [UNVERIFIED]. Clients should implement the tolerant reader pattern — critical for mobile apps that cannot be force-updated [UNVERIFIED]. URL path versioning is the recommended default: visible, cache-friendly, easy to route — maps directly to putting schema version in the catalog file path [UNVERIFIED]. Consumer-driven contract tests (Pact-style) should run in the *producer's* CI so a breaking change fails the build before production [UNVERIFIED]. Support old schema versions 6–12+ months post-deprecation with usage analytics before removal, because store-installed versions linger ("Mobile app v1.0 … expects 'name' → gets undefined → crashes") [UNVERIFIED]. (*inferred sources: API versioning/contract-testing engineering guides; digest URLs missing*)

**Apply to our design:**
- Our constraint is exactly FORWARD_TRANSITIVE: every catalog ever published must be readable by *every* installed app version. Enforce with schema-versioned paths (`catalog/v2/...`), additive-only changes within a major, and 6–12-month retention of old major paths.
- One shared KMP `Json { ignoreUnknownKeys = true; coerceInputValues = true }`; every non-essential catalog model property gets a default. Nullable-without-default fields are a code-review blocker.
- Contract tests in the publish pipeline: decode candidate catalog JSON with frozen serializer models of the oldest supported app release — the mobile equivalent of producer-side Pact.
- Avoid `@ExperimentalSerializationApi` annotations in catalog models; pin kotlinx.serialization versions deliberately.

## 3. Client networking resilience

**Retry discipline.** Clients (explicitly including mobile apps) must retry with exponentially increasing delays and discriminate by error class: network errors → retry; 4xx → usually not, because naive retries amplify overload [CONFIRMED — 3 votes, verbatim; SRE Ch. 27 "Dealing with Abusive Client Behavior"]. Every retry delay *and every periodic/automatic request* must be jittered; the SRE book's example is a phone app fetching at fixed 2 a.m., creating a nightly request barrage — choose request times randomly and jitter each backoff [CONFIRMED — 3 votes, verbatim]. (https://sre.google/sre-book/reliable-product-launches/)

**Amazon refinements** [all UNVERIFIED; *inferred source: AWS Builders' Library, "Timeouts, retries, and backoff with jitter"*]: set timeouts by acceptable false-timeout rate mapped to a downstream latency percentile (0.1% → p99.9) — but this does *not* work for internet-based clients, where worst-case network latency must be factored in. Use capped exponential backoff plus a hard retry limit. Jitter all timers and scheduled work (deterministic per-host jitter for reproducibility). Prefer local retry throttling (token bucket, in AWS SDKs since 2016) over circuit breakers (hard-to-test modal behavior, delayed recovery). Retry at a *single* layer — 3 retries/layer in a 5-deep stack = 243x load; non-idempotent calls and client errors are not safe to retry.

**Offline-first (Android guidance)** [all UNVERIFIED; *inferred source: developer.android.com offline-first architecture guide*]: the local store (Room) must be the canonical, *exclusive* source higher layers read from; reads work without network. WorkManager for persistent background sync — `Result.retry()` gives automatic exponential backoff, `NetworkType.CONNECTED` gates execution. When NOT to retry: by error type — connectivity errors retry with backoff; unauthorized requests do not retry until credentials change; a max-retry count bounds attempts. Treat connectivity monitoring as a deferral signal (queue until connected), not imperative per-request pre-flight checks. Conflict resolution: last-write-wins on timestamps requires versioning bookkeeping, network source as absolute truth — for us, the published catalog version is that truth.

**iOS background execution** [all UNVERIFIED; *inferred sources: Apple BGTaskScheduler docs + background-sync guides*]: BGTaskScheduler has no automatic periodicity — each refresh handler reschedules the next run itself (unlike WorkManager's PeriodicWorkRequest). Every task identifier must be in Info.plist `BGTaskSchedulerPermittedIdentifiers` with `fetch`/`processing` UIBackgroundModes, else scheduling fails. Register launch handlers in `didFinishLaunchingWithOptions`; submit requests in `applicationDidEnterBackground`. `earliestBeginDate` is "no earlier than" (Apple sample: 15 min), not a schedule. Every task needs an `expirationHandler` cancelling in-flight work and must call `setTaskCompleted(success:)`. Long maintenance belongs in BGProcessingTask with conditions (external power, weekly self-throttle). Both platforms floor background sync at ~15 minutes; the OS owns timing. Background scheduling/Doze cannot be reliably tested on simulators — physical devices required.

**Apply to our design:**
- Catalog refresh: conditional GET of the pointer; on failure, capped exponential backoff (1s→2s→4s… cap 60s, max ~5 attempts) with full jitter; retry only network/5xx, never 4xx; retry at one layer only (repository, not also the Ktor plugin). GETs are idempotent, so retry is safe.
- Never schedule refresh at a fixed clock time; jitter WorkManager periodic intervals and BGTaskScheduler `earliestBeginDate` so the install base doesn't hit the pointer file simultaneously — the confirmed "2 a.m. app" anti-pattern is our architecture's biggest exposure.
- Cached catalog DB is the single source of truth for all UI; fetch layer only updates it. Bundle a seed catalog for offline first launch. Model sync explicitly: `Idle → CheckingPointer → Downloading(version) → Validating → Committed / Failed(retryAt)`; commit per catalog version atomically.
- iOS: one self-rescheduling BGAppRefreshTask (pointer check) + one power-gated BGProcessingTask (rendition prefetch/cache eviction); declare both identifiers day one; QA on physical devices. Large downloads via WorkManager/URLSession background sessions, not in-process loops.

## 4. Publish pipeline reliability

**Atomic + immutable deploys.** An atomic deploy updates all code/assets/config simultaneously so content is never served partially updated; the new version receives traffic only once everything is in place — exactly the publish-then-flip property [UNVERIFIED, claims 26–33; *inferred source: Netlify/CloudCannon atomic-deploy docs*]. Non-atomic FTP-style publishing serves mixed old/new files — the motivating failure mode [UNVERIFIED]. Immutable deploys keep each version as an unchanging addressable artifact; atomic + immutable = instant rollback by re-pointing [UNVERIFIED].

**Etsy's mechanism.** Etsy deploys by fully populating a second directory and flipping a docroot symlink — content becomes visible only via a single pointer change after it is completely in place [CONFIRMED — vote 43, verbatim]. The flip itself must be atomic: create a temp symlink and rename with `mv -T`; in-place modification creates a window of missing/mixed content [CONFIRMED — vote 43, verbatim]. Atomic publish guarantees only single-request atomicity: shared resources must stay compatible *across* versions, and static assets need versioned naming so an old catalog never references missing assets [CONFIRMED — vote 44]. Pre-atomic Etsy split changes into three sequential deploys (push → switch callers → clean up) — expand/contract [UNVERIFIED]. In-flight requests keep executing against the old version (docroot pinned at request start) [UNVERIFIED]. (Etsy Code as Craft, "Atomic deploys at Etsy," July 2013)

**Staged rollout.** Nearly all Google service updates proceed gradually with verification interspersed — canary on a few machines in one datacenter, observe for a defined period, expand, then go global [CONFIRMED — 3 votes, verbatim]. (https://sre.google/sre-book/reliable-product-launches/)

**Apply to our design:**
- Enforce publish order in tooling: (1) upload all renditions, (2) upload immutable `catalog/v{N}.json`, (3) fetch the uploaded objects back through the CDN and schema-validate, (4) only then overwrite the pointer. The pointer must be a single object (our `mv -T`), never a "current/" directory.
- Immutability rule: versioned catalogs/renditions are never mutated or deleted while any pointer or installed version may reference them. Rollback = re-point to `v{N-1}`; retain N-2+ (transitive window). Content removal uses expand/contract: drop from catalog first, delete objects only after old catalogs age out.
- Canary the pointer: a `pointer-canary.json` read by a hashed percentage of installs; monitor decode-failure/crash/image-404 metrics for a bake period before flipping the main pointer — the client-side analog of Google's staged rollout.
- CI validation gates before upload: JSON-schema check, oldest-client-model decode test (§2), referential check that every image URL in the candidate catalog resolves to an already-uploaded object.

## 5. Image delivery

**Formats.** Native AVIF decode requires iOS 16+ / Android 12+ (API 31); earlier OSes need SDWebImage/libavif [UNVERIFIED]. JPEG→AVIF typically cuts 50–70% [UNVERIFIED]; worked example: 2.5MB → 1.2MB WebP vs 641KB AVIF (~75% smaller) [UNVERIFIED]. AVIF decode is more CPU-intensive than JPEG but usually nets faster on slow networks [UNVERIFIED]. Coil + AvifDecoder is the recommended Android path [UNVERIFIED]. The source gives no definitive WebP-vs-AVIF delivery verdict [UNVERIFIED].

**Firebase Storage limits.** No built-in image optimization (no auto WebP/AVIF, no compression) [UNVERIFIED]; no URL-based dynamic resize/crop — renditions must be pre-generated or handled by an external image CDN [UNVERIFIED]. A dedicated image CDN in front serves repeats from cache (first-request transform ~100–200ms) [UNVERIFIED] and does Accept-header format negotiation without URL changes — absent from raw Firebase Storage [UNVERIFIED]. (*inferred source: ImageKit blog on Firebase image optimization*)

**Cache headers** [all UNVERIFIED; *inferred source: web.dev HTTP-caching guidance*]: versioned/fingerprinted never-changing URLs → `Cache-Control: max-age=31536000`; unversioned mutable URLs (our pointer) → `no-cache` forcing revalidation; prefer ETag over Last-Modified (304 on unchanged, minimal transfer); HTTP-cache-respecting clients consult cache before network, so headers *are* the freshness policy; `immutable` directive is an optional, not universally honored, optimization.

**Apply to our design:**
- Pre-generate renditions in the publish pipeline (thumb/preview/full), since Firebase Storage cannot transform. WebP as baseline; optionally dual-publish AVIF with a per-item `formats` field, selected only on iOS 16+/Android 12+ — no third-party AVIF decoder dependency for older OSes.
- Upload-time metadata: versioned catalogs + renditions get `Cache-Control: public, max-age=31536000, immutable`; pointer gets `no-cache` + ETag so steady-state refresh is a few-hundred-byte 304.
- Decide the CDN question in the design doc: raw Firebase Storage (pre-generated renditions + correct headers) vs. image CDN (format negotiation, on-the-fly resize). Since the pipeline pre-generates renditions, defer the image CDN; revisit on bandwidth cost.
- Coil (Android) / Nuke or URLSession cache (iOS) with generous disk caches; immutable rendition URLs mean client caches never need invalidation logic.

## 6. AdMob + RevenueCat integration practices

*(All claims here are [UNVERIFIED] — no votes covered monetization. Doc-sourced but unaudited; spot-check against current Google/RevenueCat docs during implementation.)*

**UMP consent (compliance-critical).** Call `requestConsentInfoUpdate()` on *every* launch (not just first install) before showing ads; gate ad requests on `canRequestAds()` (false until that session's update call); bypassing the consent-status API can cause TCF 3.3 errors when stored consent expires, breaking ad serving. Test via `ConsentDebugSettings` (hashed test-device IDs, `setDebugGeography()` for EEA/UK/CH); UMP 2.2.0+ auto-treats emulators as test devices. Android: API 21+, `com.google.android.ump:user-messaging-platform`; structure flows to avoid redundant ad requests when both consent checks pass. (*inferred: Google UMP SDK docs*)

**Native ads in the feed.** Dev-time: dedicated native test unit `ca-app-pub-3940256099942544/2247696110`; swap before release. `AdLoader.loadAds()` batches up to five ads but is Google-demand-only and incompatible with mediation — constrains preloading if we ever mediate. Preload only as many ads as needed; expire the cache after one hour. Call `destroy()` on *every* loaded native ad, including never-displayed ones (typically `onDestroy()`). Hardware acceleration required for video creatives; never build retry loops in `onAdFailedToLoad()`. Playbook compliance: always show Ad badge + AdChoices; match feed fonts/colors while staying distinguishable; place ads during active browsing, never at navigation transitions; Google's 2017 study found native less distracting than banners; A/B test layouts via Firebase, monitor AdMob reports. (*inferred: AdMob native ads docs + Native Ads Playbook*)

**RevenueCat entitlements.** Gate premium via entitlements, not product IDs; most apps need a single entitlement unlocking everything. Product↔entitlement is many-to-many (monthly + annual → same entitlement); entitlement lifetime binds to the attached product (subscription period vs. permanent for non-consumables). Documented failure mode: new product not attached to the entitlement — users pay and get nothing. Check `customerInfo.entitlements[id]?.isActive == true` (or `entitlements.active`), never raw subscription state; an entitlement key may be *absent* even when configured (pre-purchase), so handle missing keys. `getCustomerInfo()` is cheap: locally cached, refreshed on app-active/purchase/restore and when >5 minutes old. Subscribe to the delegate/`customerInfoStream` for real-time changes. Offline: entitlements persist without internet, and the SDK can verify store purchases locally for temporary entitlements when RevenueCat servers are down, auto-disabling on recovery. (*inferred: RevenueCat entitlements/CustomerInfo docs*)

**Apply to our design:**
- Boot contract: `requestConsentInfoUpdate()` → `canRequestAds()` → init Mobile Ads SDK → load feed ads; encode as a shared-KMP state machine so Android/iOS cannot diverge; EEA debug-geography tests in QA.
- Feed ad manager: preloaded native-ad pool sized to visible need, hard 1-hour TTL, `destroy()` on eviction and screen teardown; fixed interleave intervals during browsing, never on detail-screen exit; Ad badge + AdChoices in the ad-cell design spec.
- Single `pro` entitlement (ad removal + premium wallpapers); release-checklist item: "new product attached to entitlement in RevenueCat dashboard." All gating: `entitlements["pro"]?.isActive == true`, absent key = not entitled.
- Offline-first app → rely on cached CustomerInfo + offline entitlement fallback instead of blocking premium on network; listen on `customerInfoStream` to hide ads immediately post-purchase.
